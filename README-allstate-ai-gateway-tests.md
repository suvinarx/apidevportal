# Allstate Kong AI Gateway — Use Case Test Suite

## Overview

This repository contains Bash test scripts for the Allstate Kong AI Gateway proof of concept (`sb-ai-gw`). The scripts demonstrate gateway security, logical model routing, resilience, and consumer/group token quotas.

The tests are intended for **non-production validation**. A successful test does not by itself establish production readiness.

## Gateway and model configuration

- Gateway: `sb-ai-gw`
- AI provider: AzureFoundry
- Guardrails model: `azure-gpt-5.4-mini` — route prefix `/ai/v1`
- Multi-model logical names: `high-performance`, `cost-optimized` — route prefix `/v1`
- Failover logical name: `resilient-chat` — route prefix `/v1-resilient`
- Authentication: `ai-key-auth` (API key)

At the time of inspection, `high-performance` and `cost-optimized` both targeted the same AzureFoundry deployment, `gpt-5.4-mini`. Their tests demonstrate **logical model selection**, not distinct model cost or performance characteristics.

## How to run

Use **Git Bash** on Windows or Bash on macOS. The scripts require `curl`; individual scripts may have other dependencies. The simplified multi-model routing script does **not** require `jq`.

### 1. Set the gateway URL and credentials

```bash
# Set the base hostname only when a script appends its own path.
export AI_GATEWAY_URL="https://<your-ai-gateway-host>"

# Enter the application's API key without displaying it:
read -rs -p "Kong API key: " KONG_API_KEY
echo
export KONG_API_KEY
```

**Important:** Inspect each script to see whether `AI_GATEWAY_URL` means a base URL or a complete endpoint. Do not append `/ai/v1` twice. Never commit API keys, PATs, or other secrets to Git.

### 2. Run a script

```bash
chmod +x test-multi-model-routing.sh
./test-multi-model-routing.sh
```

Other examples:

```bash
./validate-ai-consumer-rate-limits.sh
./kong_guardrails.sh
```

For resilience/failover, run the actual script filename from your repository after verifying its configuration.

### 3. Review results

Check HTTP status codes, response bodies, gateway request IDs, policy headers, and any output files generated by the script. A script's final `PASS` label is only as strong as its assertions.

## Use-case details and expected behavior

### AI guardrails

**Purpose:** Check that benign requests succeed and that disallowed or suspicious prompts receive the intended policy response.

- Benign baseline: expected HTTP 200 when authentication, routing, and upstream model are healthy.
- Prompt injection / jailbreak / encoded or indirect attacks: inspect the response body and policy decision; an HTTP 400 alone does not prove the guardrail blocked the prompt.
- Earlier observations included HTTP 503 for some cases; these require follow-up.

**Real-world scenario:** Reduce exposure to unsafe instructions or prompt manipulation before requests reach an AI provider.

### Multi-model routing

**Purpose:** Verify that the gateway recognizes the logical model specified in the JSON `model` field.

| Test | Request model | Route prefix | Expected when healthy |
|---|---|---|---|
| MM-01 | `high-performance` | `/v1` | HTTP 200 |
| MM-02 | `cost-optimized` | `/v1` | HTTP 200 |

Both logical models currently target `gpt-5.4-mini`; check gateway logs or model-routing metadata for stronger proof of selected routing.

**Real-world scenario:** Applications select an approved logical model name without hardcoding an upstream provider endpoint.

### Model resilience and failover

**Purpose:** Demonstrate fallback when a primary target fails under the configured failover criteria.

- Send a normal request through `resilient-chat`.
- Trigger a controlled primary-target failure using the approved test procedure.
- Confirm whether the configured fallback handles the request.
- Record the upstream error, fallback response, and request ID.

**Real-world scenario:** Maintain service continuity when a model provider or deployment is temporarily unavailable.

**Evidence status:** The current version of the failover script and its exact test assertions must be checked before publishing a final PASS result.

### UC-07 / UC-08 — Consumer and group token rate limiting

**Purpose:** Validate that different consumers/groups receive their configured hourly quotas and that remaining-quota headers are returned.

| Test | Consumer / tier | Observed HTTP | Quota/hour | Remaining observed | Result |
|---|---|---:|---:|---:|---|
| UC-07 | Acme Gold | 200 | 100,000 | 99,988 | PASS |
| UC-07 | Beta Standard | 200 | 20,000 | 19,988 | PASS |
| UC-08 | Gamma Partner | 200 | 50,000 | 49,987 | PASS |
| UC-07 | Acme repeat | 200 | 100,000 | 99,967 | PASS |

**What passed:** Four requests returned HTTP 200 and the expected consumer/group quota headers. Acme's remaining quota decreased across observations.

**Not yet proven:** HTTP 429 on quota exhaustion, and whether multiple consumers in the same group share one counter.

**Real-world scenario:** Enforce different usage entitlements for Gold, Standard, and Partner applications, protecting shared AI capacity and budgets.

## Troubleshooting

| Symptom | Likely cause / next check |
|---|---|
| `404 no Route matched` | Wrong path or data-plane hostname; avoid duplicate `/ai/v1` |
| `401 No API Key found in request` | `KONG_API_KEY` unset or `apikey` header missing |
| `403` | Check consumer authorization, rate-limit and guardrail policies; inspect response body |
| `503` | Check model target, provider availability, routing and gateway logs |
| `curl: (60) ... WRONG_PRINCIPAL` | TLS certificate hostname mismatch; use the correct certificate-matching DNS name |
| `jq: command not found` | Install `jq` if that particular script needs it, or use the no-`jq` variant |
| `KONG_API_KEY: unbound variable` | Export a valid API key before running the script |

Some internal diagnostic scripts use `curl -k` to bypass TLS verification. **Do not use `-k` as the production fix**; correct the certificate and DNS configuration.
